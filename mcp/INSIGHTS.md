## What Doesn't Work

- **`POST /pulls/:id/review` is FIRE-AND-FORGET and its `reviews` array is a literal `[]` on every call — a tool that renders it reports "no review was produced" on runs that succeed** (2026-08-23). `ReviewService.runReview` creates the `agent_run` rows, launches the executor with `void this.executor.executeRuns(...)`, and `return { runs, reviews: [] }` (`server/src/modules/reviews/service.ts:131-137`); the web client subscribes to SSE and refetches on `done`. Measured: the MCP call returned in 23.9 s saying "No review was produced", while the run reached `done` ~20 s later having spent $0.0061 and produced a real `approve` verdict. Fix: keep only `runs[].run_id`, poll `GET /pulls/:id/runs` until every id is terminal (`done|failed|cancelled`, `contracts/trace.ts:106`), then read `GET /pulls/:id/reviews` and join on `run_id`. Consequence for cancellation: abandoning the poll cannot cancel the run — the executor never observed the HTTP request to begin with.

## Codebase Patterns

- **An empty *successful* result must never be indistinguishable from data** (2026-08-22; the stub it described was implemented 2026-08-23, and the rule outlived it). A stub answering with an empty *successful* result is indistinguishable, to the model, from a genuine "this change impacts nothing" — the exact wrong conclusion for an impact-analysis tool. The same reasoning applies to any future tool whose backend isn't wired yet. Originally the reasoning for the `get_blast_radius` stub; the tool is real now and applies the same rule to MISSING INDEX DATA (`state: "degraded"` → `isError: true`). It also caught the fire-and-forget defect recorded under *What Doesn't Work*. Evidence: `src/tools/get-blast-radius.ts`.
- **`run_review` calls `GET /pulls/:id` before `POST /pulls/:id/review` for a reason recorded elsewhere** (2026-08-22). Do not "optimise away" that extra request — see `server/INSIGHTS.md` (2026-08-02, empty-diff / false "approve · score 100"). Cross-referenced here because the call site is in this package (`src/tools/run-review.ts`) while the evidence is in `server/`.
- **A PR accumulates one review per agent PLUS every re-run, so anything reading `GET /pulls/:id/reviews` must select the latest per agent — merging them reports SUPERSEDED findings as current** (2026-08-25). The rule already existed server-side at `server/src/modules/smart-diff/service.ts:36-38` — *"merging them would show a line flagged by a superseded run as if it were still current"* — and `get_findings` had diverged from it, flat-mapping every review. Measured on this repo's working-tree PR: **9** `Security Reviewer` reviews, and the tool surfaced a WARNING against `mcp/src/cli/demo-secret.ts`, a file already deleted, next to the current clean run. A model reading that treats a dead file as live risk. Fixed in `src/tools/get-findings.ts` (latest-per-agent by `created_at`, `all_runs: true` for history, hidden-run count always stated). Sort locally rather than trusting the API's newest-first order — that ordering is real but undeclared. Related gotcha: `get_findings` cannot reach that PR at all, because `pr` is `.positive()` and the working tree is the synthetic PR **0** the CLI writes to — the place where re-runs pile up fastest is the one the MCP surface cannot inspect.

## Tool & Library Notes

- **MCP SDK v2 (`@modelcontextprotocol/server@2.0.0`) hard-depends on `zod@^4.2.0`, while the vendored `@devdigest/shared` contracts are zod 3** (verified against installed packages, 2026-08-22). So this package may `import type` from `@devdigest/shared` (types erase; TS resolves zod 3 from `server/node_modules` for those files) but must NEVER import a runtime zod schema from there — two zod majors would be live in one process. Tool input schemas are therefore declared locally in zod 4. This is also why `mcp/` is a separate package rather than code inside `server/`, which is pinned to zod 3.
- **Claude Code loads only tool NAMES plus the server `instructions` string at session start** (verified against the Claude Code MCP docs, 2026-08-22), because tool search is on by default; full schemas arrive on demand via `ToolSearch`. Both tool descriptions and server instructions are **truncated at 2 KB each**, so critical text must come first. Measured for this server (2026-08-23, asserted by `test/context-budget.test.ts`): `tools/list` = 3 777 chars ≈ 944 tokens for all five tools; `instructions` = 448 chars. (`alwaysLoad: true` would opt out of deferral, but it is an `.mcp.json` field and this repo deliberately ships **no** `.mcp.json` — registration is local-scope and on demand, so deferral follows Claude Code's default.) Output side: Claude Code warns above 10 000 tokens of tool output and truncates at 25 000 (`MAX_MCP_OUTPUT_TOKENS`); a server can raise its own per-tool ceiling with `_meta["anthropic/maxResultSizeChars"]` up to 500 000 chars.
- **Invoke this server as `mcp/node_modules/.bin/tsx src/index.ts`, never through `pnpm`** (2026-08-22; no `.mcp.json` is committed as of 2026-08-23 — registration is local-scope via `claude mcp add`). stdout is the MCP wire: any non-JSON-RPC byte written there corrupts the session, and pnpm prints its own script banner to stdout. All diagnostics in this package go to stderr.

## Recurring Errors & Fixes

- **`ERROR packages field missing or empty` from any pnpm command in this repo is a pnpm VERSION mismatch, not a hand-written file** (2026-08-22, cause corrected 2026-08-23). `allowBuilds:` is a pnpm ≥ 10 field; **pnpm 9 rejects any `pnpm-workspace.yaml` that lacks `packages:`**, treating it as a workspace root. So the pnpm-GENERATED `server/pnpm-workspace.yaml`, `client/…`, `e2e/…` (see `server/INSIGHTS.md` 2026-08-02 on `ERR_PNPM_IGNORED_BUILDS`) are all landmines under pnpm 9 — with 9.15.9 on PATH, even `cd server && pnpm db:migrate` dies before running a line. The earlier version of this entry blamed hand-writing the file; that was only how it was first hit in `mcp/`, not the mechanism. Fixes, in order: use the pnpm the repo expects (root `README.md`: **≥ 10**); or bypass the runner — `./node_modules/.bin/tsx src/db/migrate.ts` works regardless. Do **not** hand-add `packages:` to a generated file.

## Session Notes

### 2026-08-22
- L04 `devdigest-mcp` built as a new top-level package `mcp/` (@devdigest/mcp): five tools over stdio — `list_agents`, `run_review`, `get_findings`, `get_conventions`, `get_blast_radius` (stub).
- Decision: the MCP surface speaks **`owner/name` + PR number + agent name**, never uuids, per Anthropic's tool-design guidance that inputs carry semantic identifiers a model can actually produce. `src/resolve.ts` owns the translation and every failure path enumerates the valid alternatives, so a wrong guess costs one retry rather than a dead end. Cost: one extra list call per tool call.
- Decision: **no `outputSchema`** on any tool. An output schema is pure session-start context cost for a tool whose result the model reads as prose; `format.ts` caps each tool's output instead.
- Decision: this package holds **no DB access and no business logic** — it speaks REST to the API like the web client does, so `server/src` module boundaries hold. A new capability means a new route in `server/`, not reaching past it.
- NOT verified: the live path against a running API + Postgres. Only the stdio protocol, schema shapes, validation errors, and the API-unreachable error path were exercised (`initialize` → `tools/list` → `tools/call`).

### 2026-08-23
- First run against a **live stack** (Docker Postgres + API on :3001 + real stdio JSON-RPC). This retires the "NOT verified" note above for the happy path.
- Found and fixed the fire-and-forget defect recorded under *What Doesn't Work*: `run_review` now polls `GET /pulls/:id/runs` with backoff (1 s → ×1.4 → cap 5 s, chosen against the 120/min global limit at `server/src/app.ts:96`) and reads `GET /pulls/:id/reviews` only once the runs are terminal.
- Measured, `Security Reviewer` on `sergyinfo/neoversity-dev-digest` #5: 43.8 s run, 88 579 tokens in / 785 out, **$0.0061**, verdict `approve`, 0 findings, grounding `0/0 passed`. The prompt was fully assembled (`system`, `pr_description`, `intent`, `callers`, `repo_map`), so this was NOT the empty-diff trap — that one shows ~$0.0003.
- Agent names confirmed via `list_agents`: `General Reviewer`, `Security Reviewer`, `Performance Reviewer`, all `openrouter/deepseek/deepseek-v4-flash`. A guess that the security agent might be named plain `Security` was wrong.
- **The design rule that caught the defect was our own**: an empty *successful* result must never be indistinguishable from data. Because the tool said "no review was produced" instead of rendering an empty findings list, a silent always-fails bug surfaced on the first real run instead of being read as "this PR is clean". Same rule as the blast-radius stub, different tool.

### 2026-08-23 (L04 continued)
- `get_blast_radius` is no longer a stub: it calls `GET /pulls/:id/blast`. The stub's principle MOVED rather than disappeared — `state: "degraded"` returns `isError: true` saying the impact is UNKNOWN, because an empty *success* reads to a model as "nothing is affected".
- **Ranking matters more than it looks.** Sorting the map by caller count alone put test mocks (`MockGitClient`, `MockLLMProvider`) at the top — technically the busiest symbols and the least useful thing to tell a reviewer. Sorting by endpoints reached first surfaces `taskLine` (8 routes) instead.
- The `run_review` polling loop moved to `src/review-wait.ts` and is now shared with the CLI. Both must agree on what "finished" means; the 1s → ×1.4 → 5s backoff exists because the API's global limit is 120 requests/minute (`server/src/app.ts:96`).
- `src/index.ts` was split into `src/server.ts` (the factory) + `src/index.ts` (stdio only). Not cosmetic: `serveStdio` seizes `process.stdin`/`stdout` at import time, so nothing could import the tool registry until this split. `test/context-budget.test.ts` depends on it.
- Measured budget after adding blast radius: `instructions` 448 chars, `tools/list` 3 777 chars ≈ 944 tokens — now **asserted**, not just recorded.

### 2026-08-25
- `get_findings` gained the latest-run-per-agent default and an `all_runs` parameter — defect and evidence under *Codebase Patterns*. Budget after the change: `instructions` 448 chars, `tools/list` **3 888 chars ≈ 972 tokens**, still under the 4 200-char ceiling in `test/context-budget.test.ts`; suite 89 → 92 tests. This supersedes the 3 777 / 944 figures measured 2026-08-23 above.
- **A review claim that `import { serveStdio } from '@modelcontextprotocol/server/stdio'` is a wrong path — that it should be `StdioServerTransport` from `@modelcontextprotocol/sdk/server/stdio.js` — is FALSE, and acting on it would break the build.** That is the API of the older `@modelcontextprotocol/sdk` package, which is not a dependency here and is absent from `node_modules`. The installed `@modelcontextprotocol/server@2.0.0` declares `"./stdio"` in its own `exports` map and ships `serveStdio` in `dist/stdio.d.mts`; the package's own README shows this exact import. Expect the confusion to recur — both packages are "the MCP SDK" in conversation, and the older one dominates training data and blog posts.

## Open Questions

- **2026-08-23** — `run_review` waits for *all* started runs. With `all: true` and three agents that is three sequential-ish LLM passes against one 120 s budget, and one measured pass alone was 43.8 s. Either the budget needs to scale with the number of targets, or `all: true` should return early with the run ids and defer to `get_findings`. Not decided.
