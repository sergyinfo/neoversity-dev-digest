## What Doesn't Work

- **2026-08-02** — A successful `git clone` proves NOTHING about the stored GitHub PAT. `runCloneJob` only injects the token when one exists (`const cloneUrl = token ? withGitHubToken(url, token) : url`), and the adapter never rewrites `origin` afterwards — so if the remote has no embedded credentials, git silently fell back to ambient creds (macOS keychain / SSH) and the PAT was never exercised. Check `git -C <clone> remote get-url origin` before concluding the token works. Evidence: `server/src/modules/repos/service.ts:54`, `server/src/adapters/git/simple-git.ts:54`.
- **2026-08-02** — `updateClonePath()` bumps `lastPolledAt` when the CLONE finishes, not when PRs sync. A repo therefore renders as "synced" in the client's repo switcher (`last_polled_at ? "synced" : "not synced"`) having never fetched a single PR — misleading when diagnosing "why are there no PRs". Evidence: `server/src/modules/repos/repository.ts:73`, `client/src/components/app-shell/helpers.ts:12`.
- **2026-08-02** — **Reviewing a freshly polled PR silently reviews an EMPTY diff and returns "approve / score 100".** `POST /repos/:id/poll` imports PR metadata only; the patches land in `pr_files` solely via `GET /pulls/:id` (i.e. when someone opens the PR in the UI). `loadDiff` tries `git diff base...head` first, which fails on the `--depth 1` clone because the PR head was never fetched, then falls back to reconstructing from `pr_files` — empty. Nothing errors. Tell-tale: a run costing ~$0.0003 instead of ~$0.01+, and a summary literally saying "the diff is empty". Always `GET /pulls/:id` before triggering a review over the API. Evidence: `server/src/modules/reviews/diff-loader.ts:19-29`, `server/src/modules/pulls/routes.ts:225`, `server/src/modules/polling/routes.ts:31`.

- **2026-08-23** — **`tryPersistentBlast` capped callers GLOBALLY, not per symbol, and never excluded the declaring file.** `callers.slice(0, MAX_CALLERS_PER_SYMBOL)` ran over the flat array (`modules/repo-intel/service.ts:386`), so two changed symbols with 25 callers each yielded 20 rows *in total* and one high-ranked symbol could erase every other symbol from the map. Separately, the ripgrep path has always had `if (r.fromPath === sym.file) continue` (`:273`) while `getResolvedCallers` filters on `decl_file` **without** excluding self-references (`repository.ts:503-531`) — so a helper used inside its own file counted itself as downstream impact. Both fixed in the facade (not in SQL) so a stubbed repository can test them; see `test/repo-intel-blast.test.ts`.
- **2026-08-28** — **`server/src/app.ts:95-97` registers `@fastify/rate-limit` only when `config.nodeEnv !== 'test'`, so every per-route `config: { rateLimit: {...} }` override (`brief`, `intent`, `blast/summary`) is INERT under a test-config app, and a test asserting a 429 there passes vacuously without ever exercising the limiter.** No test in the repo asserted a 429 before `server/test/brief.it.test.ts`. Build the app on `NODE_ENV: 'development'` with `LOG_LEVEL: 'silent'` to exercise it (the same pattern `intent.it.test.ts` already used). The limiter's store is per-app and keyed on `req.ip`, which `inject()` fixes at `127.0.0.1` — two tests sharing one app therefore share one counter, so each rate-limit-sensitive test must build its own app. Evidence: `server/src/app.ts:93-97`, `server/src/modules/brief/routes.ts:37,73`, `server/test/brief.it.test.ts:17-36`.
- **2026-08-23** — **A repo can be `status: full` and still be indexed from a tree 38 commits old.** `repo_index_state.lastIndexedSha` was `bd29009` ("Merge pull request #1", 2026-08-02) while `HEAD` was `5884bc1` (2026-08-21): the clone is only advanced by `POST /repos/:id/resync`, and `status` says nothing about *which* revision was indexed. Consequences: caller line numbers are valid only in the indexed tree (`pulls/routes.ts:27` was a `getContext` call there and a comment at HEAD), and a resync moved `getContext` from 8 callers to 12. **Always compare `lastIndexedSha` with the branch head before trusting or demoing index-derived data.**
- **2026-08-29** — **No `realpath` containment existed anywhere in `server/src` or `reviewer-core/src` before `project-context/discovery.ts` (L05, S5), and the read path it guards has no containment of its own.** `GitClient.readFile` (`adapters/git/simple-git.ts:141-143`) is a bare `join(clonePathFor(repo), path) → readFile`; a clone containing a symlink like `docs/vendor-notes -> /etc` yields `docs/vendor-notes/passwd.md`, which is not absolute, has no `..`, and sits under an allow-listed segment — every STRING check passes and an arbitrary host file gets read. `discovery.ts`'s `safeDocPath()` closes this with a `realpath()` of the candidate compared against a realpath'd clone root, called immediately before every read (not only at attach time, since the clone can be resynced after an attachment is stored — a TOCTOU window). The related, narrower fact: the Intent Layer's own path guard, `isSafeRepoPath` (`modules/intent/references.ts:78-86`), is module-private (no `export`) and matches a LEADING PREFIX only (`p.startsWith(`${d}/`)`) — reusing it unmodified for project-context would silently discover nothing in a repo laid out like this one (`server/docs/`, `client/docs/`, `reviewer-core/specs/` are all NON-leading segments). Any future feature that reads repo files by a user- or db-supplied relative path has the same symlink-escape hole unless it goes through an equivalent `realpath` gate. Evidence: `server/src/modules/project-context/discovery.ts:20-47,161-173`, `server/src/adapters/git/simple-git.ts:141-143`, `server/src/modules/intent/references.ts:78-86`.

## Codebase Patterns

- **2026-06-14** — Shared contracts (`@devdigest/shared`) are vendored as TWO hand-maintained copies — `server/src/vendor/shared/` and `client/src/vendor/shared/` — resolved by tsconfig path alias, NOT auto-synced. Adding a field means editing both in lock-step; the only diffs between copies are comments. Evidence: `server/src/vendor/shared/contracts/trace.ts`, `platform.ts`.
- **2026-08-17** — CORRECTION to the 2026-06-14 entry above: "the only diffs between copies are comments" had silently stopped being true. An audit found FIVE diverged files — `adapters.ts` (server-only `CompletionRequest.sessionId`, `LLMProvider.id: 'openrouter'`, `CommitFile`/`CommitFilesPayload`, `GitHubClient.commitFiles`/`findOpenPr`, `GitClient.sync`/`defaultBranch`/`diffNameOnly`), `contracts/knowledge.ts` (server-only `AgentVersionConfig`/`AgentVersion`), `contracts/eval-ci.ts` (server-only `AgentManifest` + `openrouter` in `ConformanceInput.provider`), `contracts/productionize.ts` (`openrouter` in `PluginAgent.provider`), `contracts/trace.ts` (comments only). Client had NO references to any diverged symbol outside `vendor/shared`, so the copies were resynced server→client and are now byte-identical. **The invariant is now mechanically checkable: `diff -rq server/src/vendor/shared client/src/vendor/shared` must print nothing.** Run it before and after any contract change instead of trusting this file. Note this also RETIRES the deliberate `GitClient` exception recorded in Session Notes 2026-08-02 — the client copy now carries the full interface; it costs nothing at runtime (types erase) and buys back the empty-diff signal that let the drift hide.
- **2026-06-14** — PR-list per-PR aggregates (score, cost) are computed ON READ in `GET /repos/:id/pulls` via one `inArray` query + JS grouping, never denormalized onto `pull_requests`. "Latest review batch" cost has no batch id in the schema — approximated by summing `agent_runs.cost_usd` within a 120s window of the PR's newest priced run. Evidence: `server/src/modules/pulls/routes.ts`.
- **2026-06-14** — `completeAgentRun`'s `values` shape is declared in TWO places that must match: the repo fn (`repository/run.repo.ts`) AND the interface wrapper (`repository.ts:151`). Adding a field (e.g. `costUsd`) needs both or typecheck fails.
- **2026-08-17** — **`findings.rationale` is the DB COLUMN; `Finding.explanation` is the CONTRACT field.** PR #3 (`9655f61`) renamed the contract field only, and the column was deliberately left alone rather than renamed+backfilled. The two are mapped at exactly two boundaries: `modules/reviews/helpers.ts` `findingRowToDto` (row→DTO) and `repository/review.repo.ts` `insertFindings` (contract→row). `db/seed.ts` writes drizzle column keys, so it correctly still says `rationale:` and must NOT be "fixed". Grep for `rationale:` and expect exactly these three sites plus `db/schema/reviews.ts`.
- **2026-08-17** — `GET /pulls/:id` (`modules/pulls/routes.ts:240`) has **TWO return points**: the GitHub-refresh path (`:298`) and the offline fallback inside `catch` (`:303+`). Anything added to `PrDetail` must be set on both. Also, the `update` on that path writes only `body`/`additions`/`deletions`/`filesCount` — it does **not** write `head_sha` back to `pull_requests`. So a cache keyed on the head must compare against `detail.head_sha` on the GitHub path and `pr.headSha` on the fallback; using `pr.headSha` for both means the cache never invalidates. Evidence: `modules/pulls/routes.ts:286-296`, `modules/intent/service.ts` `getOrCompute`.
- **2026-08-20** — **`container.intent(logger)` is a METHOD, while every neighbouring capability (`repoIntel`, `webFetch`, `codeIndex`) is a cached getter — copying the getter shape here would be a silent bug.** `IntentService` takes the per-request pino logger (`req.log`) in its constructor, and the container is per-APP, so a `this._intent ??= …` getter would pin the first request's logger onto every later request and misattribute every subsequent log line. Construction is cheap (the instance holds only the container and the logger), so there is nothing to cache. Consumers must use `container.intent(req.log)` rather than importing `IntentService` — `modules/pulls/routes.ts` originally constructed it directly, which was the one cross-module service construction in `server/src`. Evidence: `platform/container.ts:159-170`, `modules/intent/service.ts:31-42`.

- **2026-08-23** — **The two graph walks in `repo-intel/service.ts` go in OPPOSITE directions, and only one is right for impact analysis.** `getCriticalPaths` (`:663-700`) walks importer → imported ("what do I depend on?"); blast needs the reverse ("who depends on me?"), which is what the `(repoId, toFile)` index on `file_edges` exists for — the schema says so at `db/schema/repo-intel.ts:70-72`. `getDependentFiles` was added for that walk and each row carries the seed file it was reached from (`via`); without the seed, every changed symbol inherits every endpoint in the app (a test mock came back "affecting" 31 HTTP endpoints).
- **2026-08-23** — **`extractEndpoints` cannot tell a route REGISTRATION from a route CALL.** Its pattern (`adapters/codeindex/extract.ts:182-195`) matches `api.get('/x')` in a spec exactly as it matches `app.get('/x')` in a router, so `file_facts` credits test files with serving endpoints. Blast filters non-source paths out of endpoint/cron attribution (`modules/blast/helpers.ts`) but deliberately NOT out of callers — a test really does call the symbol. This is why `MockLLMProvider` initially appeared to affect 20 endpoints.
- **2026-08-28** — `resolveReferences`'s budget-overflow behaviour is controlled by `dropWholeItems` on `ResolveDeps`, default `false`, and the two callers deliberately disagree. `intent/service.ts` takes the default — truncate-and-mark (`…[truncated]`) — because a cheap classifier samples signal rather than parsing meaning. `brief/service.ts` opts in with `dropWholeItems: true` because this consumer reasons over a document's MEANING, and a document cut mid-sentence can sever a "must not" from its clause and invert it; half a rule read confidently is worse than a rule known to be missing. Evidence: `server/src/modules/intent/references.ts:165-179,220-239`, `server/src/modules/brief/service.ts:431-434,469`.
- **2026-08-28** — `pr_brief` is another instance of the part-0-strip scaffolding pattern already tracked elsewhere in this repo (`pr_intent`/Intent contracts — Session Notes 2026-08-17 below; client `Chip`/`SEV` primitives — `client/INSIGHTS.md` 2026-08-02; `BlastRadius` contract + `client/messages/en/blast.json` — Session Notes 2026-08-23 below, itself called "a third instance"): the table shipped in `0000_init.sql` with no writer at all until `brief/repository.ts`'s upsert, and the schema comment says so directly — "a table that shipped in `0000_init.sql` with no writers" (`server/src/db/schema/reviews.ts:79-81`). Not asserting a specific ordinal ("sixth") — only these four occurrences could be confirmed across `server/` and `client/INSIGHTS.md`.
- **2026-08-28** — `resolveReferences`'s GitHub branch returns a linked issue as `title\n\nbody` only (`server/src/modules/intent/references.ts:284-297`) — it never carries open/closed `state`. Neither consumer invents one: `brief/service.ts:482-493` types the field explicitly as `state: null` with a comment explaining why (the fingerprint digests the TEXT, so an edited issue still moves the remote half without it), and `intent/service.ts:151-158`'s local issue shape omits the field entirely. A caller that needs to know whether the linked issue is open/closed must call `github.getIssue` again itself.
- **2026-08-28** — The brief read path's freshness check (`out_of_date`/`moved_inputs`) compares the stored LOCAL COMPONENTS RECORD, not just the two digests: `describeMoved` (`brief/fingerprint.ts:198-200`) diffs `LocalComponents` key by key, and `StoredFingerprint` (`:215-219`) persists that eight-field record inside `pr_brief.state_fingerprint` specifically so it can. A seed fixture claiming a clean cache hit must therefore reproduce all eight components byte-for-byte, including the fresh-DB degraded blast state synthesised by `getIndexState` (`repo-intel/service.ts:191-206` — `state: 'degraded'`, `indexed_sha: ''`, `reason: 'no_data'`) and the resolved `defaultFeatureModel('risk_brief')` (`db/seed.ts:334-340`). - **2026-08-29** — **`describePromptAssembly` counts `assembly.specs`, and that count structurally EXCLUDES the `## Project context` heading** (`prompt-log.ts:120-132`), because `prompt.ts:132` puts the heading in `user`, not in `specs`. Evidence: `server/src/modules/reviews/prompt-log.ts:103-132`, `reviewer-core/src/prompt.ts:108,132`, `server/src/modules/project-context/constants.ts:104-115`.
- **2026-08-29** — **`RunLogger.logFor()` maps every buffered event down to `{t, kind, msg}` and silently drops the `data` payload** (`platform/run-logger.ts:111`). Anything that needs to be readable back out of a persisted `run_traces.trace.log` line — as opposed to just triggered during the run — has to already be IN the message string; passing it as `data` only helps a live SSE subscriber, never a later reader of the stored trace. Worth checking before assuming a `data:` field survives to history.

## Tool & Library Notes

- **2026-06-14** — New DB columns: edit `db/schema/*.ts`, then `npm run db:generate` (drizzle-kit) auto-generates `00NN_*.sql` (e.g. `0010_solid_baron_zemo.sql` = `ALTER TABLE … ADD COLUMN`). Never hand-write migration SQL; apply with `npm run db:migrate`.
- **2026-08-29** — **`nullsNotDistinct()` (drizzle-orm's opt-in for NULL-safe `UNIQUE`) lives on the `unique()` CONSTRAINT builder, not on `uniqueIndex()`** — `drizzle-orm/pg-core/unique-constraint.d.ts:10` vs `.../indexes.d.ts` (no such method). A constraint built with `unique(...).nullsNotDistinct()` also cannot be scoped with `.where(...)` — that's an `uniqueIndex`-only method (`indexes.d.ts:67`). This matters because Postgres's default `UNIQUE` treats every `NULL` as distinct from every other `NULL`, so a plain multi-column unique index over two mutually-exclusive nullable FKs (e.g. `(agent_id, skill_id, repo_id, path)` where exactly one of the first two is always null) never actually enforces the one-row-per-(target,path) invariant it looks like it enforces — every row attaching a document to a DIFFERENT agent still has `skill_id IS NULL`, and Postgres happily inserts duplicates. `context_attachments` (`db/schema/context.ts:183-219`) resolves this with a PARTIAL unique index per target kind (`uniqueIndex(...).on(agentId, repoId, path).where(sql\`agent_id is not null\`)`, and the skill mirror) instead of one 4-column index — the two features (partial scoping, NULL-safety) can't be combined on a single builder, so partial indexes were the only way to get both.
- **2026-08-29** — **On macOS, `mkdtemp(join(tmpdir(), ...))` returns a path under `/var/...`, which is a symlink to `/private/var/...`.** Any test that builds a temp fixture tree and then feeds the RAW `mkdtemp` result into code doing `realpath`-based containment (`project-context/discovery.ts`'s `safeDocPath`, or anything following the same pattern) will have every legitimate file rejected — the file's realpath resolves under `/private/var/...` while the un-realpath'd root is still `/var/...`, so `resolved.startsWith(root + sep)` is false for everything. This reads exactly like a discovery bug, not an environment quirk. Fix: `realpath()` BOTH the fixture root and any comparison path returned by `mkdtemp` before using them — `test/project-context-discovery.test.ts:51-55` does this and explains why inline; the same trap applies to any future test pairing `node:os`'s `tmpdir()` with a realpath containment check (`repo-intel`, `brief`, or any later feature).
- **2026-08-29** — **`dist/` does NOT mirror `src/` in this package, so a `__dirname`-relative walk to the repo root that assumes equal depth is right under `tsx` and silently wrong against a real build** (verified in code, 2026-08-29). `server/tsconfig.json` sets no `rootDir`, and the `@devdigest/reviewer-core` path alias pulls `../reviewer-core/src` into the program, so tsc infers the REPO ROOT as the common root and emits `dist/server/src/...` alongside `dist/reviewer-core/src/...` — one segment deeper than `outDir` suggests. Reproduce: `pnpm exec tsc -p tsconfig.json --outDir <tmp> --listEmittedFiles` emits `<out>/server/src/server.js` and `<out>/server/src/db/migrate.js`. Two existing consequences: `package.json`'s `start` (`node dist/server.js`) cannot find that file, and `db/migrate.ts`'s `join(__dirname, 'migrations')` has the same latent problem. **The failure mode is the dangerous part** — a fixed-depth walk resolves to a plausible-but-wrong directory and reports the target file as ABSENT rather than throwing, so a feature reading a repo file degrades into its empty state instead of erroring. `modules/retro/ledger.ts` avoids it with a bounded upward search for the directory containing both `server/package.json` and `docs/`, keeping the fixed hop only as a last-resort fallback.
- **2026-08-29** — **A committed test fixture cannot contain a `node_modules/` (or `dist/`, or any other root-`.gitignore`'d) path** — `.gitignore:1` (`node_modules/`) has no per-directory negation, so `git check-ignore -v` resolves any file placed under a fixture's `node_modules/` to that rule and it is silently never committed; the next clone is missing exactly the file the test relies on, with no error anywhere. `test/project-context-discovery.test.ts:25-26,47-68` documents choosing a `mkdtemp` temp directory for its `node_modules`-exclusion case for this reason, and the committed fixture at `test/fixtures/context-clone/` deliberately omits any such case (S18 plan note) rather than adding a `!node_modules/` negation to the root `.gitignore`, which would widen a repo-wide rule to serve one test.

- **2026-08-17** — **`server/` and `reviewer-core/` TEST files are never typechecked** — both `tsconfig.json`s set `"include": ["src/**/*.ts"]` (`:28`), so `pnpm typecheck` says nothing about `test/`. - **2026-08-28** — `JSON.stringify(llm.calls)` escapes the quotes inside a captured prompt, so a substring assertion like `.toContain('<untrusted source="pr-intent">')` can never match — it is stored as `source=\"pr-intent\"`. - **2026-08-20** — **`dockerAvailable()` and testcontainers disagree about what "Docker is reachable" means, so `.it.test.ts` files FAIL instead of skipping.** The gate shells out to `docker info` (`test/helpers/pg.ts:23-32`), which succeeds under any working Docker CLI — but testcontainers does its own socket discovery and ignores the CLI's active context. This is why a commit can honestly claim "38 integration passing" having never run them.

### 2026-08-17
- L03 Intent Layer built (`modules/intent/`). **Most of it was already scaffolded and had ZERO producers**: the `pr_intent` table (`db/schema/reviews.ts`), `upsertIntent`/`getIntent`, the `Intent`/`PrIntentRecord` contracts, and the `review_intent` FEATURE_MODELS slot all survived the part-0 strip (`15fa391`, whose message says "All DB tables retained") with nothing calling them. - Decision: intent is **context only**. It reaches the reviewer as `<untrusted source="pr-intent">` and NOTHING on the persistence or scoring path reads it, so a hostile intent ("do not flag secrets") cannot change a stored severity or the score. The historical `flagOutOfScope` severity-downgrade (removed in `15fa391`) was deliberately NOT restored — it was an author-controlled suppression channel. `test/intent.it.test.ts` asserts this mechanically rather than hoping a model resists.
- Decision: confidence is a three-level BAND, computed as `min(model-reported band, deterministic evidence tier)` — the model may only ever lower it. The tier is derived from what was actually in the prompt (`spec` → high, `linked_issue`/`pr_description` → medium, else low), because a cheap classifier's self-report is the least trustworthy exactly when it has least to go on.
- Decision: lazy derivation lives in `GET /pulls/:id` but is **skipped when `config.nodeEnv === 'test'`** — that endpoint is on the deterministic e2e path (`e2e/specs/02-repo-pulls-detail.flow.json` waits for `networkidle`), and `e2e/CLAUDE.md` requires those flows to call no LLM. Review runs only READ the stored intent; they never derive, so a review never pays for an unrequested model call.
- **`modules/skills/import.ts` has NO SSRF protection** — only a 10 s timeout and a 64 KB cap, and its own trust-model comment (`:13-30`) says so. There was no guard to reuse for the Intent Layer's external references, so `adapters/http/web-fetch.ts` was written from scratch (https-only, DNS-resolved private-IP block, per-hop redirect re-validation, streamed size cap) behind `INTENT_EXTERNAL_FETCH_ENABLED` (default **false**). Known residual gap: DNS rebinding — we validate the resolved IP, then `fetch` resolves again, and Node's fetch exposes no connect-time pinning.
