## What Doesn't Work

- **2026-08-02** — A successful `git clone` proves NOTHING about the stored GitHub PAT. `runCloneJob` only injects the token when one exists (`const cloneUrl = token ? withGitHubToken(url, token) : url`), and the adapter never rewrites `origin` afterwards — so if the remote has no embedded credentials, git silently fell back to ambient creds (macOS keychain / SSH) and the PAT was never exercised. Check `git -C <clone> remote get-url origin` before concluding the token works. Evidence: `server/src/modules/repos/service.ts:54`, `server/src/adapters/git/simple-git.ts:54`.
- **2026-08-02** — `updateClonePath()` bumps `lastPolledAt` when the CLONE finishes, not when PRs sync. A repo therefore renders as "synced" in the client's repo switcher (`last_polled_at ? "synced" : "not synced"`) having never fetched a single PR — misleading when diagnosing "why are there no PRs". Evidence: `server/src/modules/repos/repository.ts:73`, `client/src/components/app-shell/helpers.ts:12`.
- **2026-08-02** — **Reviewing a freshly polled PR silently reviews an EMPTY diff and returns "approve / score 100".** `POST /repos/:id/poll` imports PR metadata only; the patches land in `pr_files` solely via `GET /pulls/:id` (i.e. when someone opens the PR in the UI). `loadDiff` tries `git diff base...head` first, which fails on the `--depth 1` clone because the PR head was never fetched, then falls back to reconstructing from `pr_files` — empty. Nothing errors. Tell-tale: a run costing ~$0.0003 instead of ~$0.01+, and a summary literally saying "the diff is empty". Always `GET /pulls/:id` before triggering a review over the API. Evidence: `server/src/modules/reviews/diff-loader.ts:19-29`, `server/src/modules/pulls/routes.ts:225`, `server/src/modules/polling/routes.ts:31`.

- **2026-08-23** — **`tryPersistentBlast` capped callers GLOBALLY, not per symbol, and never excluded the declaring file.** `callers.slice(0, MAX_CALLERS_PER_SYMBOL)` ran over the flat array (`modules/repo-intel/service.ts:386`), so two changed symbols with 25 callers each yielded 20 rows *in total* and one high-ranked symbol could erase every other symbol from the map. Separately, the ripgrep path has always had `if (r.fromPath === sym.file) continue` (`:273`) while `getResolvedCallers` filters on `decl_file` **without** excluding self-references (`repository.ts:503-531`) — so a helper used inside its own file counted itself as downstream impact. Both fixed in the facade (not in SQL) so a stubbed repository can test them; see `test/repo-intel-blast.test.ts`.
- **2026-08-23** — **A repo can be `status: full` and still be indexed from a tree 38 commits old.** `repo_index_state.lastIndexedSha` was `bd29009` ("Merge pull request #1", 2026-08-02) while `HEAD` was `5884bc1` (2026-08-21): the clone is only advanced by `POST /repos/:id/resync`, and `status` says nothing about *which* revision was indexed. Consequences: caller line numbers are valid only in the indexed tree (`pulls/routes.ts:27` was a `getContext` call there and a comment at HEAD), and a resync moved `getContext` from 8 callers to 12. **Always compare `lastIndexedSha` with the branch head before trusting or demoing index-derived data.**

## Codebase Patterns

- **2026-06-14** — Shared contracts (`@devdigest/shared`) are vendored as TWO hand-maintained copies — `server/src/vendor/shared/` and `client/src/vendor/shared/` — resolved by tsconfig path alias, NOT auto-synced. Adding a field means editing both in lock-step; the only diffs between copies are comments. Evidence: `server/src/vendor/shared/contracts/trace.ts`, `platform.ts`.
- **2026-08-17** — CORRECTION to the 2026-06-14 entry above: "the only diffs between copies are comments" had silently stopped being true. An audit found FIVE diverged files — `adapters.ts` (server-only `CompletionRequest.sessionId`, `LLMProvider.id: 'openrouter'`, `CommitFile`/`CommitFilesPayload`, `GitHubClient.commitFiles`/`findOpenPr`, `GitClient.sync`/`defaultBranch`/`diffNameOnly`), `contracts/knowledge.ts` (server-only `AgentVersionConfig`/`AgentVersion`), `contracts/eval-ci.ts` (server-only `AgentManifest` + `openrouter` in `ConformanceInput.provider`), `contracts/productionize.ts` (`openrouter` in `PluginAgent.provider`), `contracts/trace.ts` (comments only). Client had NO references to any diverged symbol outside `vendor/shared`, so the copies were resynced server→client and are now byte-identical. **The invariant is now mechanically checkable: `diff -rq server/src/vendor/shared client/src/vendor/shared` must print nothing.** Run it before and after any contract change instead of trusting this file. Note this also RETIRES the deliberate `GitClient` exception recorded in Session Notes 2026-08-02 — the client copy now carries the full interface; it costs nothing at runtime (types erase) and buys back the empty-diff signal that let the drift hide.
- **2026-06-14** — PR-list per-PR aggregates (score, cost) are computed ON READ in `GET /repos/:id/pulls` via one `inArray` query + JS grouping, never denormalized onto `pull_requests`. "Latest review batch" cost has no batch id in the schema — approximated by summing `agent_runs.cost_usd` within a 120s window of the PR's newest priced run. Evidence: `server/src/modules/pulls/routes.ts`.
- **2026-06-14** — `completeAgentRun`'s `values` shape is declared in TWO places that must match: the repo fn (`repository/run.repo.ts`) AND the interface wrapper (`repository.ts:151`). Adding a field (e.g. `costUsd`) needs both or typecheck fails.
- **2026-08-17** — **`findings.rationale` is the DB COLUMN; `Finding.explanation` is the CONTRACT field.** PR #3 (`9655f61`) renamed the contract field only, and the column was deliberately left alone rather than renamed+backfilled. The two are mapped at exactly two boundaries: `modules/reviews/helpers.ts` `findingRowToDto` (row→DTO) and `repository/review.repo.ts` `insertFindings` (contract→row). `db/seed.ts` writes drizzle column keys, so it correctly still says `rationale:` and must NOT be "fixed". Grep for `rationale:` and expect exactly these three sites plus `db/schema/reviews.ts`.
- **2026-08-17** — `GET /pulls/:id` (`modules/pulls/routes.ts:240`) has **TWO return points**: the GitHub-refresh path (`:298`) and the offline fallback inside `catch` (`:303+`). Anything added to `PrDetail` must be set on both. Also, the `update` on that path writes only `body`/`additions`/`deletions`/`filesCount` — it does **not** write `head_sha` back to `pull_requests`. So a cache keyed on the head must compare against `detail.head_sha` on the GitHub path and `pr.headSha` on the fallback; using `pr.headSha` for both means the cache never invalidates. Evidence: `modules/pulls/routes.ts:286-296`, `modules/intent/service.ts` `getOrCompute`.
- **2026-08-20** — **`container.intent(logger)` is a METHOD, while every neighbouring capability (`repoIntel`, `webFetch`, `codeIndex`) is a cached getter — copying the getter shape here would be a silent bug.** `IntentService` takes the per-request pino logger (`req.log`) in its constructor, and the container is per-APP, so a `this._intent ??= …` getter would pin the first request's logger onto every later request and misattribute every subsequent log line. Construction is cheap (the instance holds only the container and the logger), so there is nothing to cache. Consumers must use `container.intent(req.log)` rather than importing `IntentService` — `modules/pulls/routes.ts` originally constructed it directly, which was the one cross-module service construction in `server/src`. Evidence: `platform/container.ts:159-170`, `modules/intent/service.ts:31-42`.

- **2026-08-23** — **The two graph walks in `repo-intel/service.ts` go in OPPOSITE directions, and only one is right for impact analysis.** `getCriticalPaths` (`:663-700`) walks importer → imported ("what do I depend on?"); blast needs the reverse ("who depends on me?"), which is what the `(repoId, toFile)` index on `file_edges` exists for — the schema says so at `db/schema/repo-intel.ts:70-72`. `getDependentFiles` was added for that walk and each row carries the seed file it was reached from (`via`); without the seed, every changed symbol inherits every endpoint in the app (a test mock came back "affecting" 31 HTTP endpoints).
- **2026-08-23** — **`extractEndpoints` cannot tell a route REGISTRATION from a route CALL.** Its pattern (`adapters/codeindex/extract.ts:182-195`) matches `api.get('/x')` in a spec exactly as it matches `app.get('/x')` in a router, so `file_facts` credits test files with serving endpoints. Blast filters non-source paths out of endpoint/cron attribution (`modules/blast/helpers.ts`) but deliberately NOT out of callers — a test really does call the symbol. This is why `MockLLMProvider` initially appeared to affect 20 endpoints.

## Tool & Library Notes

- **2026-06-14** — New DB columns: edit `db/schema/*.ts`, then `npm run db:generate` (drizzle-kit) auto-generates `00NN_*.sql` (e.g. `0010_solid_baron_zemo.sql` = `ALTER TABLE … ADD COLUMN`). Never hand-write migration SQL; apply with `npm run db:migrate`.

## Recurring Errors & Fixes

- **2026-06-14** — Adding a required field to a Zod contract (`RunStats.cost_usd`) breaks the inline fixture in `server/test/contracts.test.ts` (RunTrace parse). Update the `stats: {…}` fixture in the same change. Evidence: `server/test/contracts.test.ts:160`.
- **2026-08-02** — `./scripts/dev.sh` dies on a fresh clone with pnpm 11: `pnpm install` exits 1 on `ERR_PNPM_IGNORED_BUILDS` (esbuild/sharp/ssh2 postinstalls), and the script runs under `set -e`. Worse, pnpm's pre-run deps check re-runs `install` before EVERY script, so `db:migrate` and `dev` stay blocked even once `node_modules` exists. Fix: pnpm auto-generates `server/pnpm-workspace.yaml` and `client/pnpm-workspace.yaml` with `allowBuilds:` placeholders reading "set this to true or false" — set them to `true` and re-install. Those files are untracked, so each clone hits this fresh. Evidence: `scripts/dev.sh:13,73`.
- **2026-08-02** — GitHub `pulls.list` returning 404 for a repo you own, with a token that passes `POST /settings/test-connection` ("Connected as @you"), means the fine-grained PAT isn't scoped to that repository (or lacks Pull requests: Read) — GitHub returns 404 rather than 403 to avoid confirming a private repo exists. Discriminate with `GET /repos/:owner/:name`: 404 → repo not in the PAT's selected repositories; 200 + pulls 404 → missing the Pull requests permission. Evidence: `server/src/adapters/github/octokit.ts:36`.
- **2026-08-17** — **An integration test that asserts on `prompt_assembly` right after `waitForPrRuns` is RACY, and this is the root cause of the intermittent `reviews.it.test.ts` "L02: linked skills reach the model prompt" failure** (`Cannot read properties of undefined (reading 'skills')`). `run-executor` calls `repo.completeAgentRun(...)` at `:297` and only then `repo.saveRunTrace(...)` at `:342`, so a run is already terminal for a moment while `run_traces` is still empty — and `waitForPrRuns` waits on `agent_runs.status`, not on the trace. It passes in isolation and fails under parallel load. Poll for the trace itself instead. **Resolved 2026-08-20**: `waitForTrace(app, runId)` now lives in `test/helpers/runs.ts` beside `waitForPrRuns`, and both `reviews.it.test.ts` and `intent.it.test.ts` use it (the local copy in the latter was deleted). Three affected sites in `reviews.it.test.ts`, not two — `trace.config.model` at `:202` had the same defect and merely won the race more often. Full suite now 219/219 across 3 consecutive runs. **Root cause fixed 2026-08-20**: `run-executor` now writes the trace BEFORE marking the run terminal, at all three sites (`failAll`, the success path, the failure/cancel catch), so a terminal `agent_runs.status` now GUARANTEES a trace. Verified by reverting the test-side poller and running the full suite 4x against the fixed executor — 219/219 each time, where the same configuration previously failed. CORRECTION to an earlier claim in this session: SSE consumers were never exposed, because `runBus.complete(runId)` already fired AFTER `saveRunTrace` at all three sites (`:95`, `:343`, `:368`). Only observers polling `agent_runs.status` could see the window.
- **2026-08-17** — **`server/` and `reviewer-core/` TEST files are never typechecked** — both `tsconfig.json`s set `"include": ["src/**/*.ts"]` (`:28`), so `pnpm typecheck` says nothing about `test/`. Contract drift in a fixture therefore surfaces at RUNTIME, as `MockLLMProvider.completeStructured` `safeParse`s the fixture against the real schema and throws (`adapters/mocks.ts:92-95`). After any contract change, a green typecheck is not evidence the suites pass — run them. (The client is the opposite: `client/tsconfig.json` includes `**/*.tsx`, so its tests DO typecheck.)
- **2026-08-20** — **`dockerAvailable()` and testcontainers disagree about what "Docker is reachable" means, so `.it.test.ts` files FAIL instead of skipping.** The gate shells out to `docker info` (`test/helpers/pg.ts:23-32`), which succeeds under any working Docker CLI — but testcontainers does its own socket discovery and ignores the CLI's active context. Under OrbStack on macOS the CLI is fine while `/var/run/docker.sock` is a dangling symlink to Docker Desktop's `~/.docker/run/docker.sock`, so all 7 integration files die on `Error: Could not find a working container runtime strategy` at `test/helpers/pg.ts:36`. The skip promised by `pg.ts:10-11` and `server/README.md:146` therefore does NOT hold here — the suite reports 7 failed files and 38 SKIPPED tests, which is easy to misread as "integration passed". Fix: `export DOCKER_HOST=unix://$HOME/.orbstack/run/docker.sock` (check `docker context ls` for the active endpoint). This is why a commit can honestly claim "38 integration passing" having never run them.

## Session Notes

### 2026-06-14
- Re-introduced per-run cost (USD) end-to-end (lesson reversing the earlier removal in `d45ab0d`/`58c6ac7`): `cost_usd` column on `agent_runs` (migration 0010), captured in `run-executor` (was discarding `outcome.costUsd`), surfaced in `RunSummary`/`RunStats`/`PrMeta`.
- Decision: PR-list COST = sum of the latest review batch via a 120s window heuristic (no batch id in schema). Cost persisted (accurate `outcome.costUsd`), not recomputed; historical runs → null → "—".

### 2026-08-02
- Fixed `repos.default_branch` silently staying `'main'`: the column has that default, `RepoRepository.insert()` never sets it, and the list-PRs payload doesn't carry it — so a repo whose upstream default is `develop` reviewed against the wrong base.
- Decision: resolve it from the clone's own `origin/HEAD` (new `GitClient.defaultBranch()`, `git symbolic-ref --short refs/remotes/origin/HEAD`) rather than `repos.get`. Reading it locally keeps working when the PAT can't reach the REST API — exactly the case that surfaced the bug. `null` leaves the stored value alone instead of clobbering it back to the default.
- Note: the client's vendored `GitClient` copy was deliberately NOT updated — it already omits the server-only `sync`/`diffNameOnly` and `client/src` never imports `GitClient`. This is a partial exception to the lock-step rule recorded above under Codebase Patterns.

### 2026-08-17
- L03 Intent Layer built (`modules/intent/`). **Most of it was already scaffolded and had ZERO producers**: the `pr_intent` table (`db/schema/reviews.ts`), `upsertIntent`/`getIntent`, the `Intent`/`PrIntentRecord` contracts, and the `review_intent` FEATURE_MODELS slot all survived the part-0 strip (`15fa391`, whose message says "All DB tables retained") with nothing calling them. Check for that pattern before building any lesson feature — the same lesson is recorded in `client/INSIGHTS.md` (2026-08-02).
- Decision: intent is **context only**. It reaches the reviewer as `<untrusted source="pr-intent">` and NOTHING on the persistence or scoring path reads it, so a hostile intent ("do not flag secrets") cannot change a stored severity or the score. The historical `flagOutOfScope` severity-downgrade (removed in `15fa391`) was deliberately NOT restored — it was an author-controlled suppression channel. `test/intent.it.test.ts` asserts this mechanically rather than hoping a model resists.
- Decision: confidence is a three-level BAND, computed as `min(model-reported band, deterministic evidence tier)` — the model may only ever lower it. The tier is derived from what was actually in the prompt (`spec` → high, `linked_issue`/`pr_description` → medium, else low), because a cheap classifier's self-report is the least trustworthy exactly when it has least to go on.
- Decision: lazy derivation lives in `GET /pulls/:id` but is **skipped when `config.nodeEnv === 'test'`** — that endpoint is on the deterministic e2e path (`e2e/specs/02-repo-pulls-detail.flow.json` waits for `networkidle`), and `e2e/CLAUDE.md` requires those flows to call no LLM. Review runs only READ the stored intent; they never derive, so a review never pays for an unrequested model call.
- **`modules/skills/import.ts` has NO SSRF protection** — only a 10 s timeout and a 64 KB cap, and its own trust-model comment (`:13-30`) says so. There was no guard to reuse for the Intent Layer's external references, so `adapters/http/web-fetch.ts` was written from scratch (https-only, DNS-resolved private-IP block, per-hop redirect re-validation, streamed size cap) behind `INTENT_EXTERNAL_FETCH_ENABLED` (default **false**). Known residual gap: DNS rebinding — we validate the resolved IP, then `fetch` resolves again, and Node's fetch exposes no connect-time pinning.

### 2026-08-23
- L04 Blast Radius built (`modules/blast/`): `GET /pulls/:id/blast` + `POST /pulls/:id/blast/summary`, plus `POST /reviews/diff` for the pre-push CLI.
- Decision: the blast HTTP envelope is **module-local** (`modules/blast/contract.ts`), not a shared contract. Two reasons — **no route in this server declares a Zod `response:` schema** (`grep -rn "response:" src/modules` is empty), so responses are typed by TS and never validated at runtime, meaning a shared contract would buy types only; and `client/src/lib/hooks/repo-intel.ts` already keeps `RepoIntelState` local on purpose for the same data family. The MAP is the already-shared `BlastRadius` (`contracts/brief.ts:44-70`); only a seven-field envelope is declared three times. Net effect: L04 never entered `vendor/shared`.
- Decision: `getBlastRadius`'s clone-reading fallback (`service.ts:290-294`) is **never rendered**. The blast service checks `getIndexState` first and discards any result carrying `degraded: true`, because that path parses the clone during the request — which the lesson's acceptance criteria forbid. A `degraded` state means the impact is UNKNOWN and is shown as such, never as an empty map.
- **`BlastRadius` and `client/messages/en/blast.json` already existed with ZERO producers** — a third instance of the part-0-strip pattern recorded above (2026-08-17) and in `client/INSIGHTS.md` (2026-08-02). `DownstreamImpact` already had per-symbol `endpoints_affected`/`crons_affected`, exactly the shape the lesson's mockup wanted. Check for existing scaffolding before designing any lesson contract.
- `POST /reviews/diff` reuses the reviewer instead of reimplementing it by writing a synthetic PR number 0 (`pr_repo_number_uq` makes it idempotent) and letting `loadDiff` fall through to `pr_files` — base and head are both `working`, so the git attempt can never produce files. `run-executor.ts` is untouched.
- The stored `pr_files.patch` must contain **hunks only**: `diffFromPrFiles` re-adds the `diff --git`/`---`/`+++` lines itself, so keeping them produces a doubled header and a diff the parser reads as empty — the empty-diff failure mode arriving by a new road. `test/diff-review.test.ts` round-trips it.
